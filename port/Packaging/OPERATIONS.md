# Operations — configurable native host

The copied Stockroom app supports explicit `HostMode=LocalEvaluation` or `HostMode=Deployment`; `--LocalEvaluation true` remains a local-only alias. There is no automatic fallback. `Hosting/HostSettings.cs` validates required settings before transport, database, key configuration or provider access. No secrets are logged or included in the examples. The framework-dependent untrimmed build uses SDK10.0.101 and Core/ASP.NET10.0.2; later servicing patches need validation before use.

## Local evaluation

Follow README. Externally supplied disposable accounts are hashed at startup with native PasswordHasher; no enrollment, reset, lockout or credential persistence is implemented. Process-only self-signed loopback TLS and ephemeral Data Protection use a memory repository. The certificate expires after eight hours. State resets to12/version1 and cookies become invalid on restart. No trust/install operation is required. Keep demo credentials out of source/logs; unset their environment variables when finished.

## Deployment configuration

Select `DOTNET_ENVIRONMENT=Deployment` to load `appsettings.Deployment.json`. Replace all `REPLACE` placeholders and supply secrets through protected service configuration. `PublicOrigin` is the exact external HTTPS scheme/host/port, without a mount; `PathBase` is `/` or a plain prefix such as `/tenant/app`. All requests must match this origin and mount. Distinct apps need distinct hostnames because host cookies use Path=/; mount prefixes do not isolate cookies. One MVC application/global configuration per process remains required.

Identity uses native OpenIdConnect10.0.0 with IdentityModel8.16.0, authorization code with PKCE, HTTPS metadata and exact configured issuer/client audience. Register the fixed callback `<PublicOrigin><PathBase>/signin-oidc` (omit `/` PathBase) with the provider, allow code/query response, and issue `sub`, the configured NameClaim and RoleClaim in the ID token. `Editor` is the exact role that permits stock changes; other authenticated users can read. The app requests openid/profile and does not call userinfo or save access/refresh tokens. Provider-specific claim issuance and lifecycle are the operator's responsibility. Nonce/correlation handling uses the native handler with Secure, HttpOnly, SameSite=None cookies; the app auth cookie is Secure/HttpOnly/Lax in deployment, Strict locally. Remote sign-in has a five-minute bound.

Deployment disables local password endpoints. Login ignores return URL input and always returns to mounted stock. POST logout validates antiforgery and clears the application cookie, returning to mounted stock; it does not terminate the provider SSO session. A subsequent login may use that session. Provider sign-out/revocation policies, account removal, MFA and session lifecycle belong to the identity provider/operator. Application tickets expire after20minutes without sliding renewal; provider-side account/role changes may remain effective in an existing ticket for that interval. Immediate distributed revocation is not implemented. Claims are bounded and no identity-management database is introduced. Original MVC roles and request-bound CSRF still gate mutations; native authentication owns the principal before MVC begins.

Data Protection requires an absolute KeyDirectory, a stable ApplicationName unique to this deployment, and an RSA PFX Certificate path/password. `DeploymentInfrastructure.cs` explicitly uses PersistKeysToFileSystem, ProtectKeysWithCertificate and SetApplicationName; there is no unencrypted fallback or certificate-store lookup. Loading uses EphemeralKeySet, so PFX material is not imported into an OS store. The operator must provision restricted key-directory and certificate-file access, backup/recovery and suitable certificates before startup. Directory encryption protects confidentiality, not malicious key replacement: filesystem access control is essential. Keep business data outside key/certificate locations. For rotation, configure the new Certificate and up to four PreviousCertificates objects (each Path/Password) so old ring entries remain decryptable; retain old certificates and ring entries until all required payloads/backups have aged out. A wrong discriminator, lost decrypting certificate or ring removal invalidates authentication/antiforgery/TempData cookies. Do not share rings across unrelated apps.

DirectHttps binds only the configured IP/port and uses the explicit TLS Certificate PFX/password. TrustedProxy instead binds plaintext to the configured IP/port, requires1–8 explicit KnownProxies addresses and trusts only one hop of X-Forwarded-For/Proto. It never trusts forwarded Host or prefix. The proxy must overwrite forwarding headers, preserve the external Host and PathBase, terminate HTTPS and be the only permitted ingress to that listener. Host/scheme checks still reject mismatches. Network isolation, DNS, proxy controls and certificate renewal are operator responsibilities. No trusted networks or unrestricted-forwarding shortcut is supplied.

## Durable state and failure limits

Deployment uses Microsoft.Data.Sqlite10.0.0 and SQLitePCLRaw2.1.11 on an absolute State:DatabasePath. Provision its parent directory with application-only write access on local durable storage. The app creates a one-row stock table if absent; quantity0–1000 and version1–Int32.MaxValue are constrained. Local evaluation uses the original memory store. SQLite stages a parameterized expected-version update inside an immediate transaction, validates native request ownership immediately before commit, and commits once. Validation failure rolls back; stale versions return409. A five-second database busy timeout bounds contention; other storage failures surface as failures rather than fabricated success. Reload state before retrying.

This is a bounded single-host stock example, not a distributed inventory system. SQLite serializes writers. No network filesystem, multi-node topology, online schema migration, distributed transaction or high-availability claim is made. Business commit, response transmission and TempData cookie delivery are not atomic: commit can succeed before the caller sees a response. Back up the database with a supported SQLite backup procedure or after orderly shutdown; do not copy a live database arbitrarily. Preserve schema compatibility when rolling back. Session is disabled and shared response/child caches are unused in Stockroom; accepted combined-consumer evidence covers their bounded native profiles separately.

## Verification and operation

`/health` under the mount returns ready after startup. Startup logs identify loaded application/runtime assemblies; never enable token/PII logging or put secrets into logs. Maximum request body is64KiB; prepared MVC/form/JSON bounds remain. MVC rejects markup/control characters as plain single-line input, not as a general sanitizer. Spool capacity/permissions remain host responsibilities when enabling files.

The deployment identity handler is tested against a local standards fixture with generated process-only signing/TLS and ephemeral protection. Durable ordinary business data is tested by reopen and concurrent CAS. Production certificate loading, persistent key writes/rotation, external providers, proxy infrastructure and cross-restart authentication cookies are configuration/source-reviewed only and have NOT been executed in this evaluation. The trusted IHostInfrastructure composition interface allows an embedding host to supply transport/protection services; the shipped executable always chooses the concrete deployment implementation. Test fixtures and substitution code are outside the release.

Publish to a fresh versioned directory with exact feed/configuration; verify runtime, mounted health and login/edit/JSON/logout before switching the service path. Stop normally with Ctrl-C/SIGTERM. To roll back, restart the previous compatible directory with its own matching configuration and retained state/key material. Do not delete keys or downgrade an incompatible database schema. Provisioning, backup restoration and real provider integration require operator validation. The original unobtrusive browser profile is described below; fetch remains a separate workflow.

## Original unobtrusive client profile

Stockroom ships byte-identical MVC v3.3.0 `jquery.validate.unobtrusive.js` and `jquery.unobtrusive-ajax.js`, plus full jQuery3.7.1 and jQuery Validation1.22.1 under wwwroot/vendor. The runtime nupkg also provides these exact files under client/ with CLIENT-ASSETS.json; other applications explicitly copy them into their static assets and include them in that dependency order. No transitive script injection or runtime CDN is used. License texts ship under licenses. jQuery3.x is a deliberate compatibility line: original code calls parseJSON/isFunction removed in4.x. Revalidate dependencies before an upgrade; the scripts are not patched to simulate another major version.

Original MVC emits data-val/data-ajax attributes. Browser validation suppresses invalid form submission and updates field/summary feedback; all authorization, CSRF, version and server validation checks remain mandatory. Original Ajax.BeginForm posts to the same Edit action, which returns only the editor fragment when original Request.IsAjaxRequest is true. That request marker selects representation only, never trust or authorization. New fragments are reparsed through the original unobtrusive API. Named begin/success/failure/complete callbacks update status and busy state; a409 retains the form and tells the user to reload. Ajax.ActionLink reloads current stock. Native cookie challenges return401 for original Ajax requests, preserving the editor and showing a sign-in message instead of inserting the login page as a successful update. Ordinary browser navigation still redirects to login. A stale identity-bound antiforgery token can fail earlier with400; that also follows the failure path and never reports a save. With JS disabled, ordinary Edit POST still validates then redirects with one-read TempData. Native fetch is separately retained and does not replace the original scripts.

Verified profile: isolated Chromium153, local assets, root/nested mounts, ordinary stock required/number/range feedback and asynchronous save/reload. A separate package consumer demonstrates length/equal-to/remote validation, update modes and cancellation without shipping diagnostic endpoints in Stockroom. Remote validation is a read-only authenticated POST carrying native antiforgery; a client check never reserves state or grants authority. Dynamic form replacement requires explicit reparsing. Number/length rules use the pinned plugins' ordinary browser semantics; locale/globalization parity and a browser matrix are not claimed.

Callbacks are application-authored named functions; do not accept callback text, HTML update targets or returned markup from untrusted input. The unmodified Ajax script also supports dynamic function text and can invoke Function.constructor for missing/unresolved callback names. A strict CSP without unsafe-eval requires every invoked callback to resolve to a predeclared function; this sample supplies all four names and serves scripts locally. No CSP is weakened for verification, and no claim is made that arbitrary historical callback expressions work under a strict policy. HTML partials remain trusted server-rendered output; script/JSONP/cross-origin response execution is outside this profile.

References: [jQuery4 removed APIs](https://jquery.com/upgrade-guide/4.0/), [jQuery Validation1.22.1 release](https://github.com/jquery-validation/jquery-validation/releases/tag/1.22.1). Exact script hashes and upstream sources are recorded in the package client manifest.

## Area registration during native startup

Call the original `AreaRegistration.RegisterAllAreas()` or `RegisterAllAreas(state)` inside the synchronous `NativeMvcApplication.Map(endpoints, routes => { ... })` callback, before any catch-all routes that would mask the areas. The application or `FromAssemblies` catalog supplies the only assemblies inspected; duplicate assembly entries are removed. No ambient assembly scan, BuildManager hosting or disk type cache is provided. Original public concrete type/default-constructor filtering, area state and default namespace behavior are retained. Reflection order within an assembly is not a new ordering guarantee.

Registration is rejected before discovery or constructors outside the owning callback, on another thread, recursively, during endpoint binding or after route freeze. The startup reservation also rejects nested/concurrent Map callbacks. Synchronous callbacks must finish before Map returns; async-void setup is unsupported. Registration failures propagate and release startup ownership, but earlier route additions remain. Repair or clear the unbound route collection before an explicit retry; no rollback or repeat-call idempotency is promised.
